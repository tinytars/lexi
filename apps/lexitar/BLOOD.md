# Blood markers: range and interpret

How `health-dash-web` turns stored blood readings into personalized targets and a
clinical Finding. The first stage — getting lab files into the vault as
`MarkerResult` readings — is shared with every source and lives in **`INGEST.md`**.

```
  readings in vault ──▶ RANGE ──▶ per-marker target ──▶ INTERPRET ──▶ Finding
  (MarkerResult[])     Claude    (PersonalizedRange)    Claude     (ClientFinding)
```

A reading is a `MarkerResult` (`src/lib/types.ts:1`); blood readings carry
`source: "Blood"` and the lab's own reference interval in `ref` (distinct from the
personalized range below). See `INGEST.md` for how they get there, plus the
watchlist / recommended / inventory distinction that decides which markers are
ranged. The lab xlsx is now **retained in the repo** and content-hash-deduped on
re-ingest, and each reading carries a `sourceId` back to it (shared source
provenance — `INGEST.md`). Blood's stable lab-export names are exactly the
naming discipline the imaging path had to adopt (`NARRATIVE.md`).

## 1. Range — per-marker personalized target

A population reference range is not the target. For each tracked marker we ask
Claude for a **patient-specific** optimal range.

### What a range is (`src/lib/types.ts:18`, `PersonalizedRange`)

```ts
{ low?, high?, unit, explanation, explanationImperial?, generatedAt, factorsHash, generatedBy? }
```

- `low`/`high` — at least one must be set (one-sided targets allowed).
- `unit` — must match the stored reading's unit (validated).
- `explanation` — patient-facing rationale that names the factors shifting the
  range off the population default and references the typical lab range for
  comparison.
- `factorsHash` — the patient `factorsHash` at generation time. Drives staleness.
- `generatedBy` — `{mode, model}` provenance.

Stored at `client.personalizedRanges[markerName]` in the vault.

### How it's generated (`scripts/claude-ranges.ts`)

`generateRange(marker, unit, client, model, mode, usage)`:

- **System prompt** (`claude-ranges.ts:86`) injects the full patient context —
  age, gender, conditions, diagnosed disease, medications, supplements,
  pregnancy/athletic/smoking/ethnicity, BMI/height, stated goal and focus,
  notes. It instructs the model to prefer *functional/optimal* ranges over broad
  "normal" lab ranges, to keep the response unit identical to the input unit, and
  to disambiguate assays that share a unit string (e.g. free testosterone pg/mL,
  insulin, IGF-1) using the patient's recent measured values.
- **User message** (`claude-ranges.ts:189`) is one marker at a time: marker name,
  unit, and the last 5 readings (`date: value`).
- **Output** is forced to a JSON schema (`RANGE_SCHEMA`, `claude-ranges.ts:7`)
  and `validate()`'d (`claude-ranges.ts:225`): bounds present and ordered, unit
  matches, explanation non-empty, imperial explanation present for convertible
  units.

### When ranges are (re)generated

| Trigger | Path | Scope |
|---------|------|-------|
| `--refresh-ranges` | `refreshRangesFor` (`ingest.ts:482`) | watchlist + recommended (or `--marker <name>`, or `--all-markers`) |
| `--add-marker` | `autoGenerateRangesForNewMarkers` (`ingest.ts:551`) | the newly added marker, **only if it has data** |
| `--refresh-finding` | side effect (`ingest.ts:605`) | any marker the Finding newly recommends |

**Staleness:** a marker is regenerated only if `--force`, or no range exists, or
the stored range's `factorsHash` ≠ the client's current `factorsHash`
(`ingest.ts:516`). Up-to-date ranges are skipped.

**Cache warming:** the first marker runs serially to populate Claude's prompt
cache; the rest run in parallel against the warm cache (`ingest.ts:541`).

### How a range classifies a reading (`src/lib/status.ts`, `src/lib/ranges.ts`)

`resolveRange(marker, client)` is a dict lookup. `markerStatus()` then returns:

- `ok` — no range/bounds, or latest reading within bounds;
- `warn` — latest in range but some historical reading was out;
- `alert` — latest reading out of bounds.

`isRangeStale()` (`ranges.ts:7`) flags a range whose `factorsHash` no longer
matches the client — the UI uses this to mark a range as needing a refresh.

## 2. Interpret — the Finding

The Finding (`ClientFinding`, `src/lib/types.ts:121`) is the clinical narrative.
Generated by `scripts/claude-finding.ts`, triggered **on demand only** with
`--refresh-finding`.

### What it produces

- `progression` — latest / recent / overall prose.
- `disease[]` — one assessment per clinical domain, ordered by severity.
- `treatment[]` — one per current medication/supplement, deduped by drug name.
- `decisions.{patient,ai}[]` — intervention hypotheses, each with
  purpose / pros / cons / alternatives / recommendation.
- `doctorConversation[]` — questions to bring to the doctor.
- `healthMarkers.recommended[]` — markers to track, grouped by domain, each with
  a rationale; each name copied **verbatim** from the on-file census.
- `dataRequisition[]` — the re-test / re-scan schedule (see below).
- `planAssessment`, `finalThoughts`, `definitions[]`, `basis` (per-section
  attribution), plus `generatedAt` / `inputsHash` / `generatedBy`.

### What the model is given (`buildUserMessage`, `claude-finding.ts:220`)

Assembled in order: **Today** (current date, captured at build time), patient
profile, stated plan/goal, pursued study, diagnosed disease, treatment history
(each drug tagged `[Since X]` or a closed `[April–May 2026]` range), hypothesis
evaluation, patient plan, then two marker views:

1. **Markers block** — the detailed view: watchlist + previously-recommended +
   any latest-out-of-range marker, each with its personalized target (or the lab
   ref if none), last-year readings, and prior baseline.
2. **On-file census** — *every* marker with data, each tagged `[within 6mo]` or
   `[>6mo — overdue]`. This is the authoritative "what has been measured" list;
   the model may not call a census marker missing, and must copy names from it
   verbatim.

**Date awareness** (`claude-finding.ts:332`) is enforced: a treatment effect may
be attributed to a marker only if the reading was drawn *during* the dose window
and after enough time has elapsed (e.g. ≥2–4 wk for labs, ≥8 wk for HbA1c,
≥12 wk for body composition). This is why a just-started supplement is never
credited with a change.

### Data requisition rules (`claude-finding.ts:888`)

- Group by **how it is measured**: `Blood`, `Body Composition` (DEXA/scale),
  `Scan / Imaging`, `Screening / Procedure`, `Functional / Wearable`. Omit empty
  groups.
- The Blood/marker groups are a **strict view of `healthMarkers.recommended`** —
  a marker can't appear here unless it's recommended.
- Tag every marker item: `[New]` (never measured), `[Overdue]` (prior reading
  past interval / census `[>6mo — overdue]`), `[Due soon]` (within interval but a
  re-test falls in the next 6 months, event-anchored where the plan implies it).
- **Hard ceiling:** no recommended marker goes more than 6 months without a
  re-test, so every item is New / Overdue / Due soon.
- **Re-scan prior diagnoses:** walk `Diagnosed Disease` and, for each condition
  tracked by imaging/procedure whose last study is stale, requisition the
  modality that re-stages it (e.g. NAFLD / hepatic steatosis → FibroScan or
  MRI-PDFF; coronary plaque → CAC/CTA), stating the prior finding and elapsed
  time. Blood enzymes (ALT/AST) are **not** a substitute for the imaging
  re-stage of a structural diagnosis.
- Where useful timing depends on a plan step (a draw only meaningful once a drug
  is on board), make that relative timing explicit.

### Generation mechanics (`claude-finding.ts:1227`, `ingest.ts:589`)

- **On-demand only.** Skipped unless inputs changed (`inputsHash`) or `--force`.
- **prod** uses Opus with adaptive extended thinking and a 64k output ceiling;
  the large system prompt is sent with an ephemeral cache.
- Output is JSON, `validate()`'d field by field (counts, no duplicate drugs,
  `doctorConversation` length = disease + patient + ai decisions, 22 basis keys,
  etc.). **Nothing is written to the vault unless the LLM call and validation
  both succeed.**
- After a successful finding, `client.recommended` is refreshed from
  `healthMarkers.recommended`, and any newly recommended marker with data gets a
  range (the §1 side effect).

### Rendering (`src/lib/finding-render.ts`)

`buildWatchlistRows`, `buildSummaryGroups`, `buildRecommendedNoData` turn the
finding + ranges + latest readings into the on-screen tables and the PDF;
`recommendedNamesFromFinding` is what feeds `client.recommended`.

## Models, modes, cost

`inference.config.json` is the single source of truth (see `INFERENCE.md`). Today:

| Mode | Finding | Ranges |
|------|---------|--------|
| `dev` | `claude-sonnet-4-6` | `claude-sonnet-4-6` |
| `prod` | `claude-opus-4-7` | `claude-opus-4-7` |

Default is `prod`. Select with `--mode dev|prod` or `INFERENCE_MODE=`. The model
tier is a per-patient decision recorded in each artifact's `generatedBy`; confirm
a patient's tier before regenerating. Token usage and dollar cost (Opus/Sonnet
list price) are accumulated per run by `scripts/inference-cost.ts` and printed at
the end of every ingest that calls the API.

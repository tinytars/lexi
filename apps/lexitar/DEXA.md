# DEXA scans: range and interpret

How body-composition and bone-density readings are ranged and interpreted. The
**range** and **interpret** stages are the same machinery as blood markers, so
this doc only calls out what's DEXA-specific and points at `BLOOD.md` for the
shared detail. Getting a DEXA PDF into the vault as readings — the parser, the
coordinate extraction, the marker catalog — lives in **`INGEST.md`**.

DEXA readings are `MarkerResult`s with `source: "Scan"` and a body-composition /
bone `group`; the dense in-between trend can also come from `source: "Scale"`
markers (InBody export). See `INGEST.md`. The DEXA PDF / scale xlsx is now
**retained in the repo** and content-hash-deduped on re-ingest, and each reading
carries a `sourceId` back to it (shared source provenance — `INGEST.md`). DEXA's
fixed marker catalog is the stable-naming model the imaging path adopted
(`NARRATIVE.md`).

---

## 1. Range — per-marker target (shared pipeline)

DEXA markers get personalized ranges through the **same** `claude-ranges.ts` path
as blood (see `BLOOD.md §1`). What matters for body composition:

- A marker is ranged only if it's on the **watchlist** (or recommended, or named
  with `--marker`). So `--add-marker "Visceral adipose tissue mass"` is what
  makes a DEXA metric tracked and targeted; the same `plover-health-mark` skill
  applies.
- The range prompt is told to keep the response unit identical to the stored
  unit — important here because DEXA uses many distinct units (g, cm², kg/m²,
  dimensionless ratios).
- `status.ts` classifies the latest reading ok/warn/alert against the range
  exactly as for blood.

### Units / display (`src/lib/units.ts`)

DEXA values are stored raw (e.g. VAT mass in **grams**); conversion happens at
render time, not ingest:

- `displayScaleFor` auto-promotes `g → kg` when the data max exceeds 1000 g
  (`units.ts:27`) — so VAT mass shows as kg, not five-digit grams.
- `imperialOf` converts for an imperial view: `kg→lb`, `g→lb`, `cm→in`,
  `cm²→in²`, `cm³→in³` (`units.ts:3`). The ranges prompt is asked to supply an
  `explanationImperial` for exactly these convertible units.

## 2. Interpret — the Finding (shared pipeline, DEXA-aware grouping)

The Finding is generated by `scripts/claude-finding.ts` on demand
(`--refresh-finding`), same as blood (see `BLOOD.md §2`). DEXA-specific behavior:

- **Body Composition is its own data-requisition modality.** The prompt
  explicitly separates DEXA/scale-derived signals — Visceral adipose tissue
  mass, Android/Gynoid/Total % Fat, Lean mass index, Skeletal muscle mass, Body
  fat mass, Weight — into a `Body Composition` group, and forbids putting them in
  `Blood` (they're read off a scan/scale, not a draw)
  (`scripts/claude-finding.ts:888`).
- **Re-scan timing** uses the on-file census recency tags (`[within 6mo]` /
  `[>6mo — overdue]`) and the 6-month re-test ceiling, with body-composition
  re-tests often **event-anchored** to a plan step — e.g. "repeat DEXA 12 weeks
  after the Tirzepatide titration lands." This is why a DEXA re-scan shows up as
  a `[Due soon]` item tied to a treatment, not a generic annual reminder.
- **Date awareness** applies to body composition with a longer lag: the prompt
  requires ≥~12 weeks on a treatment before attributing a body-composition change
  to it (`claude-finding.ts:332`), so a just-started drug isn't credited with fat
  loss.
- **Bone density** (T-score / Z-score) and regional metrics feed the same disease
  / progression reasoning; the `Scan / Imaging` and `Screening / Procedure`
  groups also carry standard-of-care DEXA screening where age-appropriate.

Rendering (`src/lib/finding-render.ts`), the model/mode table, cost reporting, and
encryption are identical to blood — see `BLOOD.md` and `INGEST.md`.
